# Publishing to Maven Central

The namespace is `io.github.nanofaas`, verified through the GitHub organization
`Nanofaas`. The publishing account can use a personal GitHub login; the namespace
belongs to the project rather than to the account name. Java package names and
native-image metadata paths stay as they are.

## One-time setup

1. Sign in to [Sonatype Central](https://central.sonatype.com/) with GitHub.
2. Add the namespace `io.github.nanofaas`. Create the public, empty repository
   named by the portal's verification key under `Nanofaas`, then select Verify
   Namespace. Wait until the namespace is marked Verified.
3. Generate a publishing token in [User Tokens](https://central.sonatype.com/usertoken).
   Its username and password are Sonatype credentials, not a GitHub token.
4. Create a GPG signing key with `gpg --full-generate-key`. Publish its public key
   to a supported keyserver, for example
   `gpg --keyserver keyserver.ubuntu.com --send-keys KEY_ID`.
5. Configure these Actions secrets in both `Nanofaas/libcni-java` and
   `Nanofaas/containerd-java`, or as organization secrets restricted to those repos:

   | Secret | Value |
   | --- | --- |
   | `MAVEN_CENTRAL_USERNAME` | Token username from Sonatype |
   | `MAVEN_CENTRAL_PASSWORD` | Token password from Sonatype |
   | `SIGNING_KEY` | ASCII-armored private signing key exported with `gpg --armor --export-secret-keys KEY_ID` |
   | `SIGNING_PASSWORD` | Passphrase of that signing key |

Gradle imports the signing key in memory. Ordinary builds and local Maven
staging do not require publishing credentials. The Central upload task rejects
missing Sonatype credentials or a missing signing key before sending the bundle.

References: [namespace verification](https://central.sonatype.org/register/namespace/),
[tokens](https://central.sonatype.org/publish/generate-portal-token/),
[signatures](https://central.sonatype.org/publish/requirements/gpg/), and
[publication requirements](https://central.sonatype.org/publish/requirements/).

## First release order

1. Commit the libcni publication changes and push the matching `v0.24.0` tag.
   Its existing workflow runs JVM and native tests, then uploads the signed
   publication to Central with automatic release enabled.
2. Wait until `io.github.nanofaas:libcni-java:0.24.0` is downloadable from Maven
   Central. Publish this first: containerd's CI resolves the released libcni
   artifact rather than substituting a local checkout.
3. Commit the containerd publication changes and push its matching `v0.25.0` tag.
   Its workflow runs unit, integration and native checks, then publishes both
   `io.github.nanofaas:containerd-java:0.25.0` and
   `io.github.nanofaas:containerd-java-cni:0.25.0` in one Central deployment.
4. Once all three coordinates resolve from Central, update NanoFaaS's dependency,
   repository configuration and source-bootstrap pins to those released revisions.

Before the first libcni release, explicitly use the companion source checkout for
local containerd builds: `./gradlew build -PlibcniDir=../libcni-java`.
Do not move or reuse the old tags: `v0.23.0` and `v0.24.0` identify the existing
libcni and containerd releases on GitHub Packages.

## Local checks

```sh
./gradlew test publishToMavenLocal
```

To stage and inspect a signed Central ZIP without uploading it, supply
`SIGNING_KEY` and `SIGNING_PASSWORD` to `./gradlew nmcpZipAllPublications`.
POMs, sources, Javadoc and signature files are generated by Gradle's existing
publication tasks. The `com.gradleup.nmcp` plugins collect them for Central.
The upload task is `publishAggregationToCentralPortal`; normal `build` and
`check` never publish anything.
